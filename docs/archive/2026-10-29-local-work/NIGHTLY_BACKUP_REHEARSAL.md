# Historical nightly second-D1 replacement design

**Retired October 28, 2026:** the owner canceled the second production D1 and nightly schedule before activation. This file is retained as historical design context only. Do not create or configure a backup target or follow the former candidate procedure. Task 5's synthetic disposable rehearsal remains separate evidence; it is not a production backup.

The former design below was never an operating backup. It described one nightly copy at 2:00 a.m. `America/Los_Angeles`, with no additional encrypted backup, and a spring-forward skip with an administrator alert. The initial limited rehearsal imported synthetic SQL into an empty database and restored a synthetic deletion; it did **not** cover a failed import or migration ledger. The later expanded synthetic rehearsal used the current Wrangler migration set, exercised two populated replacements, verified the migration ledger, and recovered from a deliberately partial-import failure with Time Travel. Neither rehearsal used a full release dataset or establishes production recovery.

## Candidate and hard stops

On each run, acquire an exclusive lease with a durable, privately recorded run ID so two runs cannot overlap; ambiguous or stale leases require operator investigation, not automatic takeover. Verify exact account, source and target IDs against the approved private manifest, ensure the target is the dedicated backup and not production, preview or the source, and confirm exclusive access to it. Inspect supported storage version, account limits and Time Travel eligibility on the backup; obtain and record its current bookmark while the prior good copy is present. If target identity, bookmark, eligibility or prior state cannot be confirmed, **stop before mutation**. Time Travel is in-place recovery, not an independent backup or a clone; provider/account failures and an expired or unusable bookmark can make the previous copy unavailable.

Export a full source SQL file to protected transient storage, hash it and record source identity, time, tool version and expected snapshot evidence without logging private rows. Cloudflare says export blocks other database requests; allow and measure that interruption, and verify consistency and numeric fidelity with representative release data. Its documented export has restrictions on virtual tables and large integers; inspect the actual schema and data ranges. Failure to obtain and validate an export leaves the existing target untouched. Account for private transient-file access and cleanup; the owner's choice does not establish a retained second export.

The candidate replaces the populated backup by explicitly clearing only a reviewed, exact application schema and then importing the captured SQL into that target. This is **not** an atomic swap and the normal export uses `CREATE TABLE`, so blindly replaying it into an existing schema is unsafe. Before any reset, compare a private schema/table/index inventory and migration-ledger state against the approved reset plan and the export. Any unknown object, schema difference, unsupported virtual table, incomplete ledger or unexpected dependency is a stop. Never drop `_cf_KV` or other Cloudflare-managed objects. Determine and prove how the `d1_migrations` ledger is exported and recreated; do not assume the observed synthetic file represents a Wrangler-migrated production database. Prepare a release-specific reset file only after that review; a schema change invalidates it. During replacement the prior copy is unavailable, even when a bookmark permits recovery.

On any reset, import or validation failure, timeout, or ambiguous outcome, stop subsequent runs and do not mark the new copy successful. Resolve the in-flight request and recheck the exact target before further mutation. If and only if eligibility, the pre-reset bookmark, target identity and operator authorization remain valid, restore the backup target to that bookmark; retain the returned undo bookmark and verify the previous copy's expected schema, constraints, counts and representative synthetic or privately protected data. A restore can interrupt queries, can fail, and shares the same account/provider risk. If restore or verification fails, preserve evidence, alert the operator, and leave the backup marked unavailable. Never restore production to repair a backup target. Treat a successful CLI exit as insufficient without checks.

After import, verify schema and index definitions, migration ledger, foreign-key checks, uniqueness constraints, representative rows, counts and release policy values against the captured export or a consistent source snapshot, not a concurrently changing live source. Record completion, target identity and digest privately. Only then mark the new copy valid. Failed validation invokes the same recovery process. The configured administrator is the selected alert recipient; define and test the delivery mechanism, export size limits, timeout, lock ownership, credential scope, transient-file handling, and recovery owner before scheduling. A failed scheduler, skipped spring-forward run or missing alert must be visible to the operator.

## Exact disposable rehearsal outline

Use two newly identified isolated remote databases with synthetic data, named privately **SOURCE** and **BACKUP**. Record exact IDs, owner, purpose, pre-existing object inventory and eventual cleanup disposition. Verify each ID against the account before every mutating command, and verify neither is production or retained preview. Do not use environment aliases whose binding has not been checked. The commands below are examples for a pinned Wrangler version; substitute only verified private IDs and protected paths. The operation must be performed by the separately authorized remote operator; nothing here authorizes production writes.

1. Initialize both targets with the release candidate migrations using normal Wrangler migration handling. Populate SOURCE with synthetic new-state records and BACKUP with distinguishable synthetic old-state records, including realistic foreign keys and nonempty migration ledger. Record schema/table/index definitions, `d1_migrations`, counts, representative values and `PRAGMA foreign_key_check`. Confirm backup Time Travel storage version and retrieve its pre-reset bookmark:

   ```text
   npx wrangler d1 info <BACKUP_ID> --json
   npx wrangler d1 time-travel info <BACKUP_ID> --json
   npx wrangler d1 export <SOURCE_ID> --remote --output=<protected-synthetic-export.sql>
   ```

   Hash the file, inspect its schema, numeric values and migration ledger treatment, and define exact expected new state. Do not print its contents or bookmarks to public logs. Reject if the current reset plan cannot restore the entire schema and ledger faithfully.

2. After inspecting the exact candidate schema and dependencies, create and review a synthetic-only reset SQL file that removes the backup's application objects in safe dependency order. Verify its object list matches both the inspected backup and expected export, and explicitly handles the migration ledger without touching provider-managed tables. A schema-3 synthetic reset file at `backup-rehearsal/reset-schema3-synthetic.sql` passed one local populated-target replacement with a real nonempty Wrangler migration ledger and local export; `node --test backup-rehearsal/reset.test.mjs` contains that local test. It is unguarded destructive SQL for disposable local tests only: it is not a remote or production reset, does not detect unknown objects, and must not be reused without an exact independent inventory and review. The earlier remote rehearsal used an empty target and did not test this file. Record the reset file's hash and compare it before use. If a safe reset cannot be established, stop; do not improvise a blanket drop.
3. Test the success path: capture the prior bookmark, execute the reviewed reset on BACKUP, then import the exact hashed SOURCE export:

   ```text
   npx wrangler d1 execute <BACKUP_ID> --remote --file=<reviewed-synthetic-reset.sql>
   npx wrangler d1 execute <BACKUP_ID> --remote --file=<protected-synthetic-export.sql>
   ```

   Verify full expected new state, migration ledger, indexes, representative rows and constraints. Repeat a second replacement with different synthetic source values to prove it works for an already populated backup. Compare against the export/snapshot, not a changing source.

4. Test failure recovery separately: establish and record a known old backup state and a fresh bookmark; perform the reset, then deliberately execute an invalid synthetic import that fails after mutation has begun. Recheck exact BACKUP identity and wait for a terminal result, then restore its pre-reset bookmark with the documented Time Travel command. Record the returned undo bookmark; assert exact old schema, ledger, rows, constraints and counts. Repeat with interruption or ambiguous completion and a failed validation; no subsequent run may start until the prior outcome is resolved and recovery verified. Also verify alerts and lease behavior using a test harness before automation is selected. A single successful restoration does not guarantee recovery from provider or account failure.
5. Retain private commands, identity checks, tool version, timestamps, hashes, test observations and results; do not publish resource IDs or synthetic export contents. Do not delete the temporary resources as part of this task. Rehearse again when release schema, export behavior or operator tooling changes.

Schedule with an actual timezone-aware scheduler, not a fixed UTC offset. Skip the scheduled run on the spring-forward date because 2:00 a.m. local time does not occur, and alert the configured administrator. The least-effort candidate is GitHub Actions' native run notifications; schedule ownership and delivery are not configured or tested. Verify that failed runs and the intentional spring-forward skip notify the administrator. Because run notifications cannot report a workflow that never starts, a completely missed run can only be detected by a later scheduled run unless a separate monitor is added. Check scheduler behavior for restarts, duplicate execution and timezone changes; the lease and last-success monitoring must prevent overlapping or silent missed runs. No backup schedule is active.
